CardioWatch AI: from POC to market

Why it fits ITR

  • ITR builds the devices and device clouds (ECG patch, cuffless BP, biosensor ring, telemedicine SaaS). CardioWatch is the layer above: care-team alarm workflow, population analytics and integration.
  • One pipeline, many products: ingestion, data quality, alarms, audit, analytics and integration events are shared; each product adds a profile and an adapter.
  • Same delivery pattern as ITR's Canadian virtual-care platform: event-driven integration (SQS), OAuth 2.0 + RBAC, session timeouts, integrity hashes, audit log, UTC everywhere.
  • Edge and cloud AI ready: on-device events keep their model version; clinician review dispositions become labels; updates go through change control.

Release gate (IEC 62304-mapped)

In place now

  • Unit/API + UI tests in CI; E2E workflow
  • Migrations apply from empty in CI
  • Requirement → test traceability
  • No PHI in logs; audit chain verifies

Added in phase 03

  • SAST, dependency and container scans; SBOM
  • Performance and failover checks
  • Risk file review per release
  • Signed images, archived artifacts, QMS sign-off

CI/CD target

  • PR: lint, types, tests, migration check, scans
  • main: build → sign → staging → E2E → traceability report
  • release: checklist → blue/green production

Coding standards (healthcare rules)

  • No PHI outside the clinical store: never in logs, metrics, tickets or test data.
  • UTC, timezone-aware timestamps; device time and receive time stored separately.
  • Idempotent ingestion; missing, stale and implausible data never shown as normal.
  • Alarms only from clinician-approved rules or the source device; AI output carries its model version and goes to review.
  • Every clinical action audited in the same transaction; severity never conveyed by colour alone.

CardioWatch AI is a proof of concept on synthetic data. It is not a medical device, not cleared by any regulator and not HIPAA compliant; this pack describes how a team would take it there.
