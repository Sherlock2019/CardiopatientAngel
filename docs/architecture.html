What we build: one platform, many health IoT products

CardioWatch is the cardiology app and a reusable monitoring pipeline. Each health IoT product plugs in as a device profile plus an adapter; ingestion, data quality, alarms, review, audit, analytics and integrations are shared, so the next product reuses all of it.

The whole environment at a glance: two audiences, one secure backend, and two capability areas that feed it. The sections below zoom into each layer.

Application & integration architecture

Frontend, API and backend layers, with a FHIR facade so the platform plugs into existing medical systems instead of replacing them. The numbered arrows are the five core workflows, described under the figure.

The six workflows

①Daily check-in. The patient app saves answers and metrics offline, syncs when online, and calls the REST API; domain services store observations and evaluate approved alert rules.
②Care-team alerts. Workers raise an alert in PostgreSQL; the portal receives it live over SSE; a nurse acknowledges or reviews it, and every action is audited. Built in the POC.
③Plug-in apps. A SMART on FHIR app launches from the EHR and reads only what its OAuth scopes allow through the FHIR R4 API.
④EHR exchange. The resource router pulls conditions and medications from the hospital EHR, and writes back clinician-reviewed care plans only with consent and provenance.
⑤Devices and legacy feeds. Device-cloud readings (ECG patch, cuffless BP, ring) plus HL7 v2 lab feeds enter through adapters, are mapped to LOINC/UCUM, then queued, deduplicated and stored. On-device AI events keep their model version as provenance. Device fleet view built in the POC.
⑥Virtual consult. From an alarm, a clinician requests a video consult; a consult.requested event is written to the outbox in the same transaction and relayed to the virtual-care platform (bottom right). Built in the POC.

Design choices worth defending

  • Queue in front of ingestion. Device traffic is bursty and duplicated; SQS absorbs spikes, and workers de-duplicate on a natural key (device, parameter, timestamp) before writing.
  • One edge, two audiences. Patients and clinicians share the same gateway and identity layer, but get different token scopes; the API still enforces roles server-side on every route.
  • Private by default. ECS, RDS and workers live in private subnets; only the edge is public. External partners connect over PrivateLink, VPN or mTLS, never the public API.
  • Audit is a product feature. Patient-record views and alarm acknowledgments are written in the same transaction as the action, then archived immutably.

Cardiac monitoring data pipeline

How a reading travels from a device to a clinician, and what the pipeline does when readings arrive missing, late or twice.

How the POC already does this

ConcernImplementation in CardioWatch AI
DuplicatesUnique key device_id + measurement_type + observed_at; INSERT … ON CONFLICT DO NOTHING; alarms are unique on source_event_id; the simulator counts ignored duplicates
Delaysobserved_at (device) and received_at (ingestion) stored separately; a gap over 5 min sets quality_status = delayed; analytics always use device time
Missing readingsStored with a null value and quality_status = missing; device dropout raises a Signal loss advisory; trend charts show gaps rather than interpolating
ValidationPydantic bounds, allowed measurement types, units set by type, timestamps must carry a timezone
AlertsFixed, documented demo thresholds; queue ordered by source severity, not by an unvalidated model
Not yet coveredECG waveforms, FHIR Observation mapping, retry/DLQ (no queue in the POC)

ECG ≠ heart rate. A heart-rate value is one number every few seconds. An ECG is a high-frequency waveform (hundreds of samples per second, per lead). It needs its own pipeline: chunked waveform storage (e.g. S3 segments indexed in the database), specialized and validated algorithms, and a different viewer.

Seven practical safeguards

  • Least-privilege access: roles enforced server-side (in the POC: nurse, doctor, admin permission matrix).
  • MFA: through the hospital identity provider.
  • Encryption: TLS in transit; KMS-encrypted RDS, S3 and backups at rest.
  • Audit logging: record access and alarm actions written with the action, archived immutably (in the POC: audit_log).
  • Secure secrets: Secrets Manager, rotation, nothing in code (in the POC: environment variables).
  • Incident response: runbooks, on-call, breach assessment and notification.
  • Controlled use of synthetic or de-identified data: no production PHI in development or testing (the POC is fully synthetic).

Data location and offshore access

HIPAA does not impose one universal rule that patient data must stay physically in the United States. Offshore access is assessed against the applicable agreements (BAAs and client contracts), permitted uses, security controls and organizational policies, so ask what the client's data-access policy restricts.

Q. What happens if cardiac readings are missing, delayed or duplicated? Design for at-least-once delivery: idempotency keys, device and ingestion timestamps, unit validation and provenance. Missing or stale readings are marked as such, never treated as normal. Clinically significant alerts follow clinician-approved rules and escalation procedures.
Q. Can developers in Vietnam access US patient data? Only where explicitly authorized under the client's legal, contractual and security framework. Default engineering policy: no production PHI in development or testing, synthetic datasets, least-privilege access, and logged, approved production access. Any exception needs formal authorization.

CardioWatch AI is a proof of concept on synthetic data. It is not a medical device and not HIPAA compliant; this page describes a target design, not a certified deployment.
